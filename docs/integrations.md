# Integration boundaries

## Current release

Blender is the production asset tool used by this release. All island, companion and hall-upgrade assets are original, reproducible and committed with sources. The game loop is local and uses fictional resources.

Higgsfield and Handsel are **not connected at runtime**. A Codex plugin connection never grants this game that user's credentials or tool access. No API keys belong in browser code.

## Higgsfield: optional production pipeline

Useful next assets: one consistent four-character portrait sheet, an illustrated chapter opening, and a short final beacon cinematic. Use Blender geometry as the consistency reference; retain the editable source and the generated output separately.

Art brief: “Guildwake, a quiet low-poly adventure on a floating island. Oxidized copper roofs, mossy conifers, warm limestone, brass lanterns; calm blue-green evening light. Companions are a green-cloaked scout, rust-cloaked craftsperson, blue-cloaked guardian and violet-cloaked chronicler. No text, no UI, no photorealistic humans.”

A real adapter must preflight cost/authorization, store one generation job ID before polling, avoid paid duplicate retries, download outputs to an asset manifest, and validate format/license/visual consistency. Higgsfield 3D Jutsu is a separate remote workspace, not this machine's Blender process. Browser/plugin access available in Codex does not imply an app API entitlement.

## Handsel: organizations and asynchronous work

Potential mapping: guild → Office, expedition plan → delegation/session, companion job → subtask, returned media → artifact. Keep Handsel's real-money job paths out of the default game simulation.

Start with a separately configured **read-only** organization/status connection, or an explicitly approved development environment. Later use server-side scoped credentials and idempotent identifiers for external production work. A local expedition result is not a Work Proof signature and cannot release escrow.

Do not submit every movement or random encounter to an LLM. Keep combat/movement/game state in the game engine. Agent reasoning, if introduced, proposes a constrained action; authoritative rules validate it.

## Blockchain phase

Only introduce an authoritative shared state after the local game loop is tested with players. Suitable records: guild ownership, trade contracts, resource transfers, objectively verifiable delivery. Rendering, generated media and movement remain outside the chain.

Local save edits, client RNG, UI “success” text and mocked WebMCP results are never settlement evidence. A multiplayer/chain version needs server/contract authorization, replay protection, authoritative randomness, exploit testing, and a testnet milestone before any real value is enabled.

## First playtest

Ask five people to start without instructions. Observe whether they select two companions, launch, resolve an encounter, claim rewards and discover rest/upgrade. Target three players completing the chapter and two voluntarily starting another expedition. Track where they hesitate; do not interpret game-item earnings as business revenue.
